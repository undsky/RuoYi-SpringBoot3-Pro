# Query 工作流

基于知识库回答问题。核心理念：**每次查询都应让知识库变得更好**。

> 📌 **路径约定**：`raw/`、`gen/`、`wiki/` 均指当前知识库（`<project>/kb/`）下的绝对路径，
> 由 SKILL.md 路由时确定（`KB_RAW`、`KB_GEN`、`KB_WIKI`）。`KB_LANG` 为该知识库的语言设置。

## 工作流程

### 1. 理解问题

判断输入类型：

| 类型 | 特征 | 去哪 |
|------|------|------|
| **知识查询** | 正常的知识问题 | 步骤 2-5 |
| **操作偏好/反馈** | 对操作方式的偏好（"回答要标注来源"） | 步骤 4d |
| **答案纠正** | 对上次回答的纠正（"你说错了，其实是 XX"） | 步骤 4a 修正对应页面 |
| **偏好 + 纠正** | 兼有（"回答太浅了，XX 应该补充 YY"） | 4a 补内容 + 4d 记偏好 |

**设计原则**：wiki 本身就是记忆。内容错误/不足通过修正 wiki 页面解决（下次查询自然答对），
不需要额外记「教训」。`conventions.md` 只存偏好规则，不存纠错历史。

知识查询则识别关键词、涉及的实体和概念。

### 2. 检索相关页面

按顺序：

1. 读 `wiki/index.md`，据关键词定位可能相关的页面
2. **检查 `wiki/analyses/` 是否已有相关历史分析** — 避免重复劳动，在已有分析上深化
3. 读定位到的 wiki 页面
4. 需要更多上下文 → 用 Grep 在 `wiki/` 下搜关键词
5. 涉及原始细节 → 查 `gen/` 里的全量产物（`raw/` 原件是再下一层，见下）

#### 什么时候该下潜到 `gen/`

wiki 页面是压缩过的，`gen/` 里的产物是全量的。这些情况值得下潜：

- 用户要**原话/精确引用**（"他到底怎么说的"）→ 读 `gen/` 找原句，附时间点
- 用户问的细节**摘要页没覆盖**（某个具体数字、某段的完整论述）
- 需要**核对转写质量**（页面上标了 `（转写待核）` 的地方）

下潜前先看 source 页 frontmatter 的 `derived_file` 拿路径（值形如 `gen/xxx.txt`，
相对知识库根解析）。摘要页够用就不要下潜 ——
全量文本又长又碎，读它是有成本的。

`raw/` 原件是再下一层，回答问题时基本不需要 —— 只有产物本身可疑（疑似漏字、乱码）
或用户要看原始版式/图像时才碰，且只读不改。

### 3. 综合回答

- 直接回答问题
- 引用具体 wiki 页面作为来源：`（参见 [[page-name]]）`
- 引用转录素材的原话时带时间点：`（[[interview]] [12:34]）`
- **有相关历史分析就在其上深化**，而非从头开始
- 信息不足时明确说知识库缺什么
- 有矛盾信息时列出不同来源的不同说法

### 4. 知识回写（自进化核心）

每次 query 完成后评估是否产生新知识：

#### 4a. 自动回写（不需确认）

- **补充信息**：综合出了某个 entity/concept 页尚未记录的信息 → 追加内容，更新 `updated`
- **新增交叉引用**：发现了之前未关联的页面间联系 → 双方 Related 都加链接
- **修正小错误**：发现页面里的事实性错误 → 直接改
- **消除转写疑点**：下潜 `gen/` 后确认了某处 `（转写待核）` 的真实内容 → 更正并去掉标记

#### 4b. 建议回写（需确认）

- **值得独立成页的分析**：比较分析、综合论述、新发现的关联 → 存为 `wiki/analyses/` 新页面
- **新实体/概念**：回答涉及了 wiki 里还没有的重要实体或概念 → 建议建页
- **矛盾发现**：发现已有页面间的矛盾 → 建议标注

建议格式：

```
📝 本次查询产生了以下知识更新：

自动更新:
  - 更新了 [[memex]]，补充了与现代 RAG 系统的对比
  - 在 [[vannevar-bush]] 和 [[knowledge-management]] 之间加了交叉引用

建议操作:
  - 💡 将本次对比分析存为 wiki/analyses/memex-vs-rag.md？
  - 💡 为 "RAG" 建概念页 wiki/concepts/rag.md？
```

#### 4c. 回写执行

用户确认后：

- 创建新页面（完整 frontmatter + Related 区块）
- 更新相关已有页面的 Related（双向链接）
- 更新 `wiki/index.md`
- 更新 `wiki/overview.md`（统计变化时）
- `wiki/log.md` 记一条：`## [YYYY-MM-DD] query | 问题简述`

#### 4d. 用户反馈回写（自动执行）

输入是操作偏好或反馈时触发。

| 分类 | 判断依据 | 示例 |
|------|---------|------|
| Query | 回答方式、输出格式、引用风格 | "回答要标注来源"、"比较类问题用表格" |
| Add | 收录策略、页面拆分、命名偏好 | "一笔带过的概念不要建独立页"、"实体页标题用中文" |
| Convert | 转换参数偏好 | "音频一律开说话人分离"、"OCR 默认按繁体识别" |
| Test | 检查偏好、修复策略 | "P2 问题不用报告"、"断链自动修复不用确认" |
| 通用 | 跨操作的通用偏好 | "所有操作用中文回复"、"操作完成后给一行摘要就行" |

执行步骤：

1. 读 `wiki/conventions.md`（不存在则按初始模板创建）
2. 判断分类，以 `- ` 列表项追加到对应区块
3. **去重**：已有语义相同的条目就更新它，不重复添加
4. **精炼**：同分类超过 10 条时，合并语义相近的条目
5. 更新 `updated` 日期
6. 告知用户记到了哪个分类

> ⚠️ 不要把操作偏好存到 Claude Code memory，统一存进知识库自己的 `conventions.md`
> —— 偏好属于这个知识库，换个知识库就该换一套。

### 5. 回答格式

按问题类型选：

| 问题类型 | 格式 |
|---------|------|
| 事实查询 | 简短回答 + 引用 |
| 比较分析 | Markdown 表格 |
| 综合论述 | 结构化长文 |
| 时间线 | 按时间排列的列表 |
| 概览 | 思维导图式层级列表 |
| 汇报分享 | Marp 幻灯片 |
| 数据对比/趋势 | matplotlib 图表 |
| 关系梳理 | Obsidian Canvas |

## 注意事项

- **语言**：按 `KB_LANG`，回答和新建页面统一用目标语言
- 优先用 wiki 里已综合好的信息，而不是每次从原始素材重新推导 —— 这是本方法论与 RAG 的根本区别
- **历史分析复用**：analyses/ 下已有相关分析就在其上深化
- 明确区分「wiki 中记录的信息」和「LLM 自身知识」
- 问题完全超出知识库范围时告知用户，并建议收录相关素材
- 自动回写要克制：只补确定性高的信息，不写推测
