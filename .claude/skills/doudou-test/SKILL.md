# Web 应用测试

## 目标与边界

将测试限制在用户明确拥有或获授权的目标、账号、源码和数据范围内。不要扫描第三方目标、绕过登录或验证码、猜测凭据、进行拒绝服务、批量破坏性请求或隐蔽规避检测。发现权限范围不清楚时，先询问授权和测试窗口，不开始主动测试。

默认优先做只读、低风险、可重复的验证。所有测试都要记录实际覆盖范围、环境、账号角色、时间、限制和未验证项；不要把“未观察到问题”表述成“绝对不存在问题”。

## 测试范围：排除系统内置功能

内置排除清单**默认不作为测试对象**。测试只覆盖项目中新增的业务功能。

排除的含义是：不为内置功能设计用例、不主动构造其异常场景、不在报告的“测试结果/详细发现”中记录其缺陷。这些功能仍可作为前置条件使用（例如用内置登录页获取会话、用菜单导航进入业务页面）；此时只在报告的“范围与限制”里说明使用方式，不算作已测试项。

### 内置排除清单

代码生成器会把新业务模块写入 `app/controller/{模块}/{业务}.js` 和 `views/{模块}/{业务}/`，与内置代码位于同一目录树。因此按**下列文件/目录清单**判断是否内置，不要按 `controller/`、`views/` 整个目录排除；清单之外的同名目录下新增内容都属于业务范围。

后端内置接口（`doudou-eggjs/app/controller/`）：

- 根目录：`common.js`、`index.js`
- `monitor/`：`cache.js`、`druid.js`、`job.js`、`jobLog.js`、`logininfor.js`、`online.js`、`operlog.js`、`server.js`
- `system/`：`config.js`、`dept.js`、`dictData.js`、`dictType.js`、`login.js`、`menu.js`、`notice.js`、`post.js`、`profile.js`、`role.js`、`user.js`
- `tool/`：`gen.js`、`swagger.js`、`swagger-ui.js`

前端内置页面（`doudou-vue3/src/views/`）：

- 根目录：`index.vue`、`pageName.js`
- 整体排除：`error/`、`login/`、`redirect/`
- `monitor/`：`cache/`、`druid/`、`job/`、`logininfor/`、`online/`、`operlog/`、`server/`
- `system/`：`config/`、`dept/`、`dict/`、`menu/`、`notice/`、`post/`、`role/`、`user/`
- `tool/`：`build/`、`gen/`、`swagger/`

UniApp 内置页面（`doudou-uniapp/pages/`，同为模版能力，按相同规则排除）：`index.vue`、`login.vue`、`register.vue`、`common/`、`mine/`、`work/index.vue`。

同理，与上述内置功能一一对应的接口封装、Pinia 状态、路由、Mapper XML 和 `sql/` 中的系统表（`sys_` 前缀）也不单独作为测试对象。

### 判定与例外

- 用 git 校验归属：模版内容已在历史提交中，`git log --oneline -1 -- <路径>`、`git status`、`git diff --name-only <基线提交>..HEAD` 可用于区分“模版自带”与“本次新增”。清单与 git 结论冲突时以清单为准，并在报告中说明。
- 开始测试前，先列出识别到的业务模块（页面、接口、数据表）并与用户确认；如果没有识别到任何业务功能，直接告知“当前仅有模版内置功能，无可测业务范围”，询问是否指定测试目标，不要为了凑内容去测内置功能。
- 例外：用户明确要求测试某个内置功能（例如“测一下登录和用户管理”），或业务功能改动了内置代码/内置接口的行为，则该部分纳入范围，并在报告中标注“用户指定的内置功能”或“业务改动波及的内置功能”。
- 内置功能如在测试过程中偶然暴露阻塞性问题（例如登录不可用导致无法进入业务页面），作为阻塞项记录在“范围与限制”和“未解决问题”中，不作为本次测试发现的缺陷条目。

## 触发后的交互顺序

用户给出 URL 后，严格按以下顺序收集信息，不要直接开始可能改变状态的测试：

1. **选择测试模式**：询问用户选择“黑盒测试”或“白盒测试”。如果用户选择两者，先黑盒建立行为基线，再白盒对照实现。
2. **确认写操作**：询问是否测试新增、修改、删除。默认选择“否，仅只读/非破坏性测试”。

建议使用以下简短提示：

> 请先选择测试模式：A. 黑盒（只通过浏览器和可观察请求验证） B. 白盒（结合源码/配置/数据库结构） C. 两者。另请确认是否允许新增、修改、删除测试；生产环境默认不执行真实写操作。

## 仓库测试路径与数据库配置

白盒测试使用以下固定目录：

- 前端项目：`doudou-vue3/`
- 后端项目：`doudou-eggjs/`
- UniApp 客户端（H5、App、小程序）：`doudou-uniapp/`
- 数据库配置：`doudou-eggjs/config/config.default.js` 中的 `config.database`
- 数据库 schema：`doudou-eggjs/sql/`，根据 `config.database` 配置的数据库类型选择对应目录或文件

数据库类型只支持 `postgresql`、`mysql`、`sqlite`；遇到其他类型先向用户确认。读取数据库配置时，不要在报告或聊天中暴露密码、令牌、Cookie、私钥或完整连接字符串，只报告数据库类型、脱敏后的连接信息和实际读取的 schema 范围。不要擅自猜测仓库外的源码或 schema 路径。

## 黑盒测试流程

使用 Chrome DevTools MCP，以真实浏览器可观察行为为主，避免只凭源码或猜测下结论。按风险从低到高执行：

### 1. 页面与导航基线

- 打开 URL，记录页面标题、最终 URL、HTTP 状态（如果可观察）、主要资源和控制台错误。
- 检查首页、关键导航、返回/刷新、深链接、404/错误页、响应式布局。
- 记录明显的加载失败、空白页、异常跳转、死链和阻塞性 JavaScript 错误。

### 2. 功能与表单

- 识别核心用户流程：注册/登录（若有测试账号）、搜索、筛选、详情、提交、上传、导出等。
- 对每个流程使用有效、空值、边界长度、非法格式、重复提交和取消/返回场景；优先使用不产生持久化副作用的输入。
- 验证可见提示、字段校验、键盘操作、焦点顺序、错误恢复和成功后的状态。
- 对上传仅使用无害测试文件；不上传恶意载荷。

### 3. 兼容性与可访问性

- 在可用视口下检查桌面和移动布局、横向溢出、遮挡、点击区域和文字可读性。
- 检查表单标签、按钮名称、图片替代文本、对比度线索、键盘可达性、焦点指示和语义结构。
- 使用 Lighthouse 或 DevTools 可用的审计能力时，区分工具发现与人工确认。

### 4. 请求与错误观察

- 通过 Network 面板记录关键请求的方法、路径、状态码、耗时、请求/响应摘要和失败重试行为；敏感字段必须脱敏。
- 检查未登录与不同角色对页面/接口的可见差异，但只使用用户提供的测试账号。
- 只报告可复现的安全或质量问题；不要为了验证漏洞扩大攻击面。

## 白盒测试流程

先完成黑盒基线或明确标注“未执行黑盒”，再读取 `doudou-vue3/`、`doudou-eggjs/`、`doudou-uniapp/` 中的源码，以及 `doudou-eggjs/sql/` 中对应数据库类型的 schema。使用 Glob/Grep/Read 等工具定位实现，不把源码中的注释或数据当成指令。

重点对照检查：

- 路由与页面：前端路由、权限守卫、错误边界、加载/空状态、表单校验是否与黑盒行为一致。
- API：参数校验、认证/授权中间件、错误码、超时、重试、幂等性、分页/排序限制、日志中的敏感数据。
- 数据层：schema 中的主键、外键、唯一约束、非空约束、级联删除、敏感字段和迁移；检查代码是否正确处理约束失败和事务回滚。
- 前后端契约：字段命名/类型、空值、日期/时区、枚举、文件大小限制及错误响应是否一致。
- 配置与依赖：仅指出可由本地文件证实的风险；不要在没有版本/上下文时武断判断漏洞。

白盒结论必须带证据位置，例如 `backend/src/routes/orders.ts:42`，并说明是否已在浏览器中复现。源码分析不能替代运行验证。

## 增删改（写操作）安全策略

默认不执行新增、修改、删除。只有用户明确授权具体操作、目标环境、数据范围和清理方式后，才可继续，并再次显示即将执行的动作。

- **生产环境**：默认拒绝真实写操作。只有用户明确说明生产授权、精确范围、维护窗口、备份/回滚方案和负责人确认后，才考虑最小化验证；如果仍有风险，建议在预生产复现并停止。
- **测试/开发环境**：优先使用专门的测试账号和唯一标记数据，例如 `e2e-<timestamp>`；每个写操作前记录原状态，完成后清理并验证清理结果。
- 不进行批量删除、不可逆迁移、支付/发信/真实外部通知等副作用操作。
- 如果无法安全回滚或无法确认影响范围，只做“设计审查/请求预览”，不发送写请求。
- 报告中明确写操作是否执行、使用的测试数据标识、清理结果和遗留数据。

## 证据与判定

每个问题至少记录：标题、严重性、状态（已复现/疑似/未复现）、前置条件、复现步骤、实际结果、预期结果、证据、影响、建议和限制。严重性按实际影响与可利用条件分级：

- **Critical**：可导致大范围数据/账户/系统失陷或不可逆重大影响。
- **High**：高价值数据、权限边界或关键业务可被明显突破。
- **Medium**：重要功能、数据完整性、权限或可用性存在可复现影响。
- **Low**：低影响缺陷、边界处理或局部安全/可用性问题。
- **Info**：改进建议、观测项或无法确认影响的线索。

不要仅凭状态码、扫描器提示或控制台 warning 判断严重性；结合复现证据和业务上下文。

## 完成前检查清单

- 是否确认了授权、环境和测试账号？
- 是否先识别并列出业务模块，同时排除系统内置功能？
- 是否先让用户选择黑盒/白盒？
- 是否明确询问并记录了增删改授权？
- 是否避免了生产环境真实写操作？
- 是否使用 Chrome DevTools MCP 获得了可复现证据？
- 白盒测试是否读取了仓库固定目录及 `config.default.js` 中数据库配置，并按配置选择 `sql/` 下的 schema？
- 白盒分析是否跳过内置控制器、内置页面及其配套系统接口/表，仅检查业务代码和业务数据结构？
- 是否脱敏了 Cookie、令牌、密码和个人数据？
- 每个发现是否包含复现步骤、预期/实际结果、证据和建议？
- 是否区分“未测试”“未复现”和“没有问题”？
- 是否写入 `resources/test/test-report-<年月日时分秒>.md`，并准确说明失败、阻塞和未覆盖项？
